# 原版 2.4.6 直接升级正式 2.4.13：Windows 定向验证

日期：2026-11-05。

**结论：原版 2.4.6 存在成功直升 2.4.13 的自动安装路径，无需经过中间版，也无需预先修改旧代码或使用恢复工具。** 本次通过的是无历史待确认记录、仅注册知识库包的有效隔离 profile。安装返回需要重启，重新启动 Host 后确认正式 2.4.13 生效。不能将这一结果推广为所有 2.4.6 profile 均可自动成功。

## 验证对象与方法

- 旧包：正式 `local-dsh-knowledge-base-2.4.6.tgz`，构建 `5c9679e46cbc1498`，SHA-256 `dba33f268771d01435aafa6bf331fb00d83901daeaab2353c2bdc3832ca93c45`。
- 目标：正式 `local-dsh-knowledge-base-2.4.13.tgz`，构建 `280919e50a3d55eb`，SHA-256 `a7966d297df119573d85a4cbca532359beab1018fd469f387a0a496cc8984b49`。
- 完整解出公开旧包后核对其构建。调用原包中的自动决策、客户端更新状态机、Host adapter HTTP API、下载器、Python 事务安装器及运行服务，没有替换成新安装器或补丁。
- 宿主接口由最小测试外壳提供，HTTP API 和后台服务真实运行，pnpm 真实执行。原客户端函数在 VM 中执行，浏览器存储由独立内存对象替代。下载接口返回固定摘要的正式清单和 TGZ 原始字节，不将联网或镜像可用性纳入本次结论。
- 新版确认在另一个全新 Node Host 进程中执行，避免模块缓存继续复用旧代码。所有库内容、依赖名称、历史回执及状态均为隔离合成数据，没有使用正式用户 profile。

## 结果

| 场景 | 实际结果 | 旧版保留情况 |
| --- | --- | --- |
| 无旧回执、仅知识库依赖 | 原版自动决策触发检查、下载、准备和提交；事务 `committed`，返回 `restart-required`。新 Host 加载 2.4.13 后，新客户端自行确认并清除该次待确认记录 | 旧服务有匹配的干净退出回执；合成原件不变 |
| 已有失效的旧 Host 回执 | POST 状态确实缺 build，GET 有 build；原客户端停在待确认，没有调用准备安装 | 旧包及 profile 清单/锁不变，旧服务仍 active |
| profile 内其他插件使用相对 `file:` 依赖 | 原版旧安装器在准备阶段拒绝，未调用提交安装 | 旧包及 profile 清单/锁不变，旧服务仍 active |
| 新增 SDK 固定版本不在原锁文件及离线缓存中 | 旧安装器重新解析 profile 时准备失败，未调用提交安装 | 旧包及 profile 清单/锁不变，旧服务仍 active |

SDK 场景有意包含缺失的锁记录，不能据此断言所有已完整锁定的私有 SDK 都会失败；它证明旧准备流程对需要重新解析、但离线不可用的其他依赖仍会受阻。

成功场景的新运行服务构建为 `996f2d95de9faa74`，与正式 2.4.13 代码一致。没有运行恢复工具，没有安装任何中间版本，没有用新版本的更新器替代旧版本来执行首次提交。

命令：`node --test tests/direct-246-upgrade.test.mjs`。4 个子场景断言全部通过（Node 汇总计入外层测试共 5 项）。后三个子场景通过是指预期阻断及旧版保留成立，不代表升级成功。

## 边界

本次没有驱动完整 DSH Electron 窗口，也没有验证自动重启、真实用户的全部插件组合、在线更新源可达性、真实解析任务或模型调用。成功场景按原版返回结果执行一次新 Host 启动，不能宣传为完全无操作的激活。已被旧状态阻断的实例仍需独立恢复，详见 [恢复说明](../UPDATE-RECOVERY.md)。
